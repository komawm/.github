# Koma workspace guidance

Start from the [workspace map](https://github.com/komawm/.github/blob/main/workspace/workspace.toml), then read the owning repository's agent guidance: [Koma](https://github.com/komawm/koma/blob/main/AGENTS.md), [Jiku](https://github.com/komawm/jiku/blob/main/AGENTS.md), [types](https://github.com/komawm/koma-types/blob/main/AGENTS.md), [docs](https://github.com/komawm/docs/blob/main/AGENTS.md), [packaging](https://github.com/komawm/packaging/blob/main/AGENTS.md), or [organization](https://github.com/komawm/.github/blob/main/AGENTS.md). This root is routing only, with no Git or CarryCtx project. The map distinguishes six owned independent repositories and external references, never submodules.

Koma owns the nine compositor/tool crates. Jiku owns the desktop orchestration agent and its bundled skills; there is no separate jiku-skills repository, and avatar work is deferred. Koma-types owns versioned Lua configuration types, koma-docs (remote `komawm/docs`) owns canonical Koma/Jiku specifications, and packaging owns distribution packaging and CD. Use one root `LICENSE` per repository: GPL-3.0-or-later for Koma/Jiku, Apache-2.0 for koma-types, and MIT for docs/packaging/organization infrastructure. Preserve third-party notices and moved design documents as specifications, not acceptance evidence.

[Phodopus](https://github.com/Xuepoo/phodopus) is outside the Koma organization and is an external shared dependency with its own identity, licensing, history, and state. It may be a user-managed symlink to another workspace. Do not change its origin, initialize another CarryCtx project through its link, modify its upstream configuration, or silently redirect Cargo resolution to a workstation checkout. Resolve and inspect the actual target read-only when needed.

Run Git, Cargo, CarryCtx, hooks, and quality gates inside the owning checkout. Register a named agent, start a session, record scoped tasks and dependencies before multi-step changes, and leave checkpoints with evidence and remaining work. CarryCtx state is per repository, stored under its Git common directory. Read task state back and verify changes before completion. Use isolated worktrees when delegating code after a first commit exists; before that, explicitly disjoint file scopes are required. Follow the [vendored CarryCtx skill](https://github.com/komawm/.github/blob/main/workspace/.agents/skills/use-carryctx/SKILL.md). Never publish raw state or private snapshots.

The [organization repository](https://github.com/komawm/.github) owns the root templates and agent commands. Update the source and deploy through its non-destructive bootstrap script. Keep repository identity fields consistent with the map; map keys and descriptor names identify local checkouts and repository URLs identify remotes. Use canonical HTTPS URLs in README and AGENTS documentation so independent clones remain understandable. Keep applicable CI commands aligned with each repository's justfile. Docs only needs local Markdown checks, with no CI/CD or issue/PR/review requirement. Packaging uses local packaging checks and CD without a generic CI or issue/PR requirement; product artifacts belong in the corresponding Koma/Jiku GitHub Releases when publication is authorized. Existing implementation, architecture proposals, compilation evidence, runtime observations, and security acceptance are distinct claims.

The six `komawm` repositories are published on GitHub (`remote_changes_enabled = true`) and configured from the [declarative GitHub plan](https://github.com/komawm/.github/tree/main/github). Koma uses `v0.0.x` incubation versions until independently accepted `v0.1.0` release readiness; follow the [release plan](https://github.com/komawm/.github/blob/main/docs/releases.md). Apply meaningful issue/PR labels and milestones consistently across published repositories. The user plans to install CodeRabbit; its review is additional evidence, and missing remote access does not block local setup. Follow the supplied `code-review` and `autofix` skills when those tools are used.

Use `/tmp/koma/` for disposable files and ignored `recording/` for durable local evidence, VM images, and read-only external reference clones under `recording/references/` (such as `Hyprland` and `niri`). Keep original assets and VM images outside tracked files. Use `ISO_PATH` to discover the user's read-only ISO collection; do not hardcode its workstation location. Record VM command lines and tool versions alongside evidence.

The development host is Arch Linux with Hyprland and a dedicated GPU. Tool availability and device access must be checked in the current execution environment: the agent process may not see the host's GPU or KVM. Validate models and protocols first, then nested compositor behavior, then isolated QEMU/KVM sessions. Nested or software rendering does not prove DRM/KMS, physical input, GPU passthrough, or BSD support. Do not replace the current desktop session, install system services, bind a GPU, alter boot configuration, or modify host device permissions without an explicit task authorizing it.

Use ordinary user-owned paths and installed tools such as Git, gh, Cargo, Bun, just, lefthook, CarryCtx, Podman/Docker, and QEMU. Run the [environment doctor](https://github.com/komawm/.github/blob/main/scripts/doctor.py) to inspect availability. Remote publication and releases require explicit user intent; workspace initialization alone does not publish the organization or prove product readiness.
